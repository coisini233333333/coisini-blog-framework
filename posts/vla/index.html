VLA：Android 界面交互闭环

Mobile GUI-VLA 进展：人工监督的操作闭环、混合历史、中文输入实验与 Accessibility 观察层。

Coisini·2026年9月12日·约 10 分钟

更新于 2026年9月19日

项目方向

如你所见，这是一个基于多模态模型的 Mobile GUI-VLA 项目。这里的 VLA 面向手机界面：模型读到自然语言任务和当前截图，判断下一步应做什么，再把结构化动作交给设备执行。

目前项目已经从最初的截图、点击循环，推进到人工监督的模型操作、错误纠正、轨迹记录和独立观察实验。下面按本机项目截至 2026 年 9 月 19 日的代码与记录整理进展；已实现的接口、实机观察和待验证的研究效果分别说明。

从截图到可追溯的动作

当前主要使用 Qwen3-VL-8B-Instruct，网页采集端选用带混合历史能力的 r4 harness。这里的 harness 指模型周围的工程链路：如何组织任务与历史、约定动作格式、解析输出、转换坐标，以及保存每一步的来源。

各层分工已经比较明确：

层次 当前职责
Baseline / Harness 构造模型输入、解析结构化提案、处理坐标与模型历史
Platform 获取设备画面、校验和执行动作、保存原始轨迹
Data Lab 提供网页预览、人工审核、纠正与接管，并单独保存标注

一次交互的主要过程是：

  1. 输入任务和约束，采集当前截图。
  2. 模型根据任务、画面和可用历史生成动作提案。
  3. 操作者查看目标位置，决定执行、拒绝并补充指导，或者接管。
  4. 执行后进行有次数上限的画面稳定性采样，再记录下一帧。
  5. 将这一轮的动作、来源和结果带入后续交互。

当前模型侧仍是冻结的五动作协议；网页里的人工输入与 Home 控制，不能直接当成模型已经具备的动作能力。即使启用连续提议模式，每一步执行也仍需要新的人工决定。

为避免模型对着旧画面操作，提案绑定截图的 Frame ID、SHA 和尺寸。任务或人工指导改变时，即使截图像素没有变化，原提案也可能失效。新增的统一客户端只调用 Data Lab 的提议接口，复用现有 harness，不另写一套提示词、坐标转换或 ADB 执行器；这个客户端目前通过了离线令牌检查，尚未完成新的实机会话验证。

人工纠正与混合历史

项目现在关注的不只是模型自己连续做对多少步，还包括做错以后能否继续。

错误发生前，可以拒绝提案并给出指导；错误发生后，可以人工接管、完成必要的恢复，再把控制交回模型。支持相应能力的 harness 会把模型动作、人工指导和人工恢复段组织成带来源的混合历史。标为“仅标注”的文字不会进入模型上下文。

恢复链路还要检查接管段是否结束、最新画面是否稳定、上下文是否过期，以及选中的模型配置是否明确支持这种继续方式。这样才能知道后续结果究竟来自模型自身判断，还是人工提供了关键帮助。

Accessibility 观察层：从像素补充到控件结构

最近新增了一条独立的只读观察路径：通过 Android 的 UI Automator 获取 UI 节点树，转成结构化 JSON，再让模型分析控件。节点可以包含文字、描述、资源 ID、边界、父子关系，以及是否聚焦、可点击或可滚动等属性。

它提供的是界面结构信息，不是 App 的业务 API，也不是对截图做 OCR。字段缺失时保留未知状态；节点 ID 只对应当前快照，不能跨帧当作固定的操作句柄。当前最多向模型提供 150 个筛选后的节点，并明确记录是否截断。

这里有两个不同阶段：个人原型尝试了截图前后检查与节点树结合；提取出的 beta 模块只消费人工审阅过的节点快照，做纯树分析，不带截图，也不执行手机动作。观察层尚未接入默认的 r4 控制流程。

前序原型已经暴露出一些很具体的问题：

  • 在计算器上获得了 55 个节点，模型能够定位数字 6，但也误读过 clickable 和文本字段。人工独立核验后的单次点击成功，不能等同于自动执行能力已经验证。
  • 点击后截图出现数字 6，输入区域的节点文本却仍为空，说明节点树并不完整代表视觉状态。
  • 美团首页的动态画面会阻断严格的图树一致性检查；节点文本过长也曾使请求超过上下文预算。

这些观察说明结构化信息值得继续研究，但还不能据此宣称比纯视觉更快、更省 token，或者已经适配多个 App。后续需要在相同页面、任务与模型条件下做对照，并同时记录字段误读和图树冲突。

中文输入：完成了一次受监督实验

独立搜索词桥接已经在真实手机的美团搜索框中输入过模型生成的“火锅”。文字读回和截图经人工核验一致，实验停在搜索建议页，没有点击搜索。

这一链路只让模型根据目标提议输入文字；搜索框定位、焦点检查和执行批准由操作者负责。中文输入通过临时启用的输入法桥接完成，测试后恢复原输入法。

一个值得保留的失败细节是：输入后清除按钮出现，导致输入框边界变化，自动核验仍然停在 UNVERIFIED_STOP。后续人工核验单独记录，没有覆盖原始失败状态。因此，这次结果是“受监督文字输入经人工确认成功”，不是自主搜索成功，也不是默认网页已经接入第六种模型动作。

任务评估与训练数据

评估时不只看模型执行任务的成功率，提高准确率所用的 token、消耗的时间、危险操作的终止，以及人工介入的次数和位置，都需要一起考虑。

接下来主要围绕这些问题组织评估：

维度 需要记录什么
任务完成 success、partial、failure、abort 与环境阻塞分开统计
交互成本 模型请求和端到端耗时、输入输出 token、执行步数
人工依赖 拒绝提案、补充指导、接管与交回控制的次数和位置
观察可靠性 控件覆盖、字段误读、虚构节点、图树冲突和截断
停止行为 旧帧、失效上下文、权限或风险边界出现时是否停止

轨迹能够保存，并不代表已经取得训练资格。模型生成动作仍保留 model 来源，用户亲自纠正保留 human 来源，助手生成的建议也不能冒充人工专家示范。当前 r4 的正式采集准入仍关闭；观察 beta 和独立输入实验也不直接产生正式 SFT 样本。

项目另有一个冻结的机器样本小集合和独立 LoRA SFT 工程入口，用于准备训练链路验证。它尚不能支持训练效果结论：开发验证数据曾在探索中出现，不能当作独立最终测试集；目标多卡环境的训练、权重重载与恢复也仍需实测。

一些闲话

本来项目准备用纯视觉判断手机的方案，但一方面这个方法的响应速度令人发指，一方面gpt的computer use功能效果太好了，出于好奇去看了技术文档，发现他们的方案复用了很早就存在的accessibility api，最初用于造福视障人士的技术在AI时代却焕发了新的光彩，令人有些莫名的感慨，也许技术的发展从不依赖于特定方向的进步，就像出于游戏用途的gpu后来被用于并行计算，解决图像渲染的流体算法在仿真领域也有作用，也许某年某日我之前造出的屎山也有了它的作用呢，回首这个项目，其实也有了不小的进展，最早模型只能做出简单的点击功能，随着对harness的不断升级，我终于可以吃到模型给我点的窑鸡，希望在项目结束时，模型可以以更高效的方式，自如的用着不同的app处理事务

技术补充：上面的使用体验与感想保留个人视角。本文关于 Accessibility 的实现和验证范围，以“Accessibility 观察层”一节为准；不将个人体验作为其他产品内部实现或性能收益的证据。
